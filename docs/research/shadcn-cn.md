# `shadcn-ui/cn` research

Checked 2026-09-05 against release `cn@0.2.5`.

## Findings

- **Package:** the exact npm package is [`cn`](https://www.npmjs.com/package/cn), installed with `npm i cn`. The published package is currently `0.2.5`, MIT-licensed, dependency-free, dual ESM/CJS, and marked `sideEffects: false` ([package manifest](https://github.com/shadcn-ui/cn/blob/main/packages/cn/package.json), [release](https://github.com/shadcn-ui/cn/releases/tag/cn%400.2.5)).
- **It replaces both packages:** `cn(...inputs)` combines `clsx` argument handling (strings, arrays, objects, numbers, and conditionals) with Tailwind conflict resolution, so it is a drop-in replacement for the common `twMerge(clsx(...))` wrapper. The root entry also exports compatible `clsx`, `twJoin`, and `twMerge` functions. Maintainers test merge output against `tailwind-merge`; one exception is `experimentalParseClassName`, which is not supported ([README](https://github.com/shadcn-ui/cn/blob/main/README.md), [root source/API](https://github.com/shadcn-ui/cn/blob/main/packages/cn/src/index.ts), [types](https://github.com/shadcn-ui/cn/blob/main/packages/cn/src/types.ts)).
- **Current API:** `cn` exports `cn`, `clsx`, `twJoin`, `twMerge`, and `createEngine`; `cn/config` exports `createCn`, `createTwMerge`, `extendTailwindMerge`, `fromTheme`, `validators`, `defaultConfig`, and `mergeConfigs`; `cn/engine` exposes the compiled-table engine; `cn/lite` provides strings-only `clsx/lite` parity. The package additionally exposes `cn/tables` and `cn/compiler`. The CLI is `npx cn build` ([README API list](https://github.com/shadcn-ui/cn/blob/main/README.md#api), [exports map](https://github.com/shadcn-ui/cn/blob/main/packages/cn/package.json), [`cn/config` source](https://github.com/shadcn-ui/cn/blob/main/packages/cn/src/config.ts)).
- **Tailwind compatibility:** the shipped rules target **Tailwind CSS v4**, including v4 prefixes via `createCn({ prefix: "tw" })`. The maintainers explicitly say Tailwind v3 users should remain on `tailwind-merge` v2 ([README gotchas and custom themes](https://github.com/shadcn-ui/cn/blob/main/README.md#gotchas)).
- **Runtime requirements:** maintainers describe the runtime as framework-agnostic and usable in browsers, Node, Bun, Deno, and edge runtimes. Published ESM and CJS are compiled to **ES2022**, so older browsers require transpilation; no exact supported-browser matrix is published. The npm manifest declares **Node >=20** (and the README specifically states the CLI needs Node 20+) ([README](https://github.com/shadcn-ui/cn/blob/main/README.md), [build target](https://github.com/shadcn-ui/cn/blob/main/packages/cn/tsdown.config.ts), [package engines](https://github.com/shadcn-ui/cn/blob/main/packages/cn/package.json)).

## Performance and design tradeoffs

- `cn` compiles Tailwind conflict configuration into flat typed-array lookup tables. Runtime merging uses a single-pass trie plus argument, whole-string, and token caches rather than interpreting a config/trie and regex validators on each call. This favors repeated component renders and startup speed, but introduces mutable caches and a larger engine ([design](https://github.com/shadcn-ui/cn/blob/main/docs/how-it-works.md)).
- Maintainer benchmarks report 30x for the common stable-argument call, 1.9x for warm/cache-hit strings, 3-6.4x for cold workloads, 7x for first call, and a 37x geometric mean over calls harvested from 58 repositories. These are project-authored microbenchmarks, not independent results; the methodology isolates processes, warms each implementation, and keeps the best of five, while acknowledging run-to-run variance and synthetic cold cases ([benchmark table](https://github.com/shadcn-ui/cn/blob/main/README.md#how-much-faster), [methodology](https://github.com/shadcn-ui/cn/blob/main/docs/how-it-works.md#benchmark-methodology)).
- The default entry is about **10.5 KB min+gzip**, roughly **1.9 KB more over the wire** than `clsx + tailwind-merge` (~8.6 KB), although its minified parse size is slightly lower (26.2 vs 27.4 KB). Runtime custom configuration costs about 15 KB and compiles lazily on first use (~3 ms). `cn build` can generate smaller project-specific tables, but dynamic class construction needs a safelist, stale development tables can temporarily miss newly introduced groups, and build-time subsetting should not be shipped by component libraries because consumer classes are unknown ([size analysis](https://github.com/shadcn-ui/cn/blob/main/docs/how-it-works.md#size), [`cn build` guidance](https://github.com/shadcn-ui/cn/blob/main/docs/build-setup.md)).

## Recommended usage

For a Tailwind v4 application, use the default zero-config entry first:

```ts
import { cn } from "cn"
```

For an existing shadcn/ui app, run `npx shadcn@latest migrate cn`, or replace the local `twMerge(clsx(inputs))` wrapper with `export { cn } from "cn"` and remove `clsx` and `tailwind-merge` if nothing else imports them ([migration instructions](https://github.com/shadcn-ui/cn/blob/main/README.md#existing-shadcnui-project)). Use `createCn` from `cn/config` only for custom merge rules. Use `cn build` only when bundle size or zero-cost custom themes justify a code-generation step; the maintainers recommend the default import for most apps and advise against generated subsets in published libraries ([build guidance](https://github.com/shadcn-ui/cn/blob/main/docs/build-setup.md#when-to-use-it)). If dependencies still import the old packages, bundler aliases can remove duplicates, subject to documented limits around default `clsx` imports, custom `extendTailwindMerge`, and libraries that inline their own merge code ([aliasing guide](https://github.com/shadcn-ui/cn/blob/main/docs/aliasing.md)).
