# Maxime Heckel on design tokens

Checked 2026-09-05. The article was published in 2022; repository links below describe current `main` and are supporting evidence, not necessarily the exact implementation discussed then.

## What Heckel recommends

- **Use primitive color scales behind semantic aliases.** Heckel's "two-tier color variable system" puts palette values such as `--blue-10` in the first tier and intent-bearing aliases such as `--brand` and `--foreground` in the second. Components consume the aliases, not literal palette tokens, so a brand color or theme mapping can change without rewriting components. The alias layer can also compose primitives, including opacity ([article: Color system](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#color-system)).
- **Semantic color aliases carry design intent across themes.** Light and dark themes can map the same role to different primitive steps. Current source still follows that model: both theme files define numeric color scales and then map roles including `--accent`, `--background`, `--danger`, `--text-primary`, and `--input-focus`; `Button` styles consume those role names rather than fixed blue/gray steps ([article: Color system](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#color-system), [light theme](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/themes/light.ts), [dark theme](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/themes/dark.ts), [Button styles](https://github.com/MaximeHeckel/design-system/blob/main/src/components/Button/Button.styles.tsx)).
- **Not every primitive needs a semantic alias.** Heckel lets components reference spacing, type-size, and radius scales directly because he expects those values to change less significantly than colors. His naming rule is numeric suffixes incremented by `1` for ordinary size scales and by `10` for scales likely to need insertions, so future additions need not rename existing tokens ([article: Other tokens and Naming](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#other-tokens)).
- **Treat tokens as a maintained, malleable layer.** Component work repeatedly caused him to add, refine, combine, and delete tokens. He explicitly rejects the idea that tokens are immutable bedrock and tries to keep their number as small as possible, balancing system complexity against consistency ([article: Lessons learned](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#lessons-learned)).
- **Preserve intent in component state styling too.** His component-local custom-property pattern declares defaults near the top, uses those variables in the main CSS body, and has variants and interaction selectors reassign them. This keeps transitions and hover/focus/active logic readable while allowing experimentation ([article: Variant driven components](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#variant-driven-components), [current Button implementation](https://github.com/MaximeHeckel/design-system/blob/main/src/components/Button/Button.styles.tsx)).
- **Prefer one owner package when simplicity is the goal.** For his small, personal system, Heckel chose one branded package, `@maximeheckel/design-system`, so there is one library to version. He pairs that choice with tree-shakable ESM entry points and versions design-language changes as major, additions as minor, and updates/fixes as patch ([article: Versioning](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#versioning), [article: Bundling](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#bundling), [package manifest](https://github.com/MaximeHeckel/design-system/blob/main/package.json), [build configuration](https://github.com/MaximeHeckel/design-system/blob/main/esbuild.build.js)). Current source centralizes global token and theme installation in the package's exported `globalStyles` ([global styles](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/globalStyles.ts), [public exports](https://github.com/MaximeHeckel/design-system/blob/main/src/index.ts)).
- **These are contextual choices, not universal laws.** Heckel calls his token naming "far from perfect," describes the system as personal and small-scope, and says his component decisions reflect having one developer/consumer and personal preference ([article: Context](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#context-why-would-i-even-choose-to-build-my-own-design-system), [article: Naming](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#other-tokens), [article: Component patterns](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#component-patterns)).

## Our adaptation

- **Brand the namespace, not the meaning.** Heckel demonstrates a branded npm scope and current branded theme selectors (`.maximeheckel-light` / `.maximeheckel-dark`), but he does not recommend brand-prefixed custom properties; his properties remain generic. For a reusable multi-consumer package, we should add a short stable package prefix to globally exposed properties to avoid collisions, while retaining semantic roles inside it, for example `--anaphor-color-accent` rather than either unscoped `--accent` or value-bound `--anaphor-blue-button` ([package manifest](https://github.com/MaximeHeckel/design-system/blob/main/package.json), [light theme](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/themes/light.ts), [dark theme](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/themes/dark.ts)).
- **Keep ownership aligned with the dependency direction.** The design-system package should own primitive scales, semantic mappings, theme selectors, and the global installer; components should depend on that contract. Applications may choose or override semantic mappings, but should not duplicate the primitive source of truth. This extends Heckel's single-package organization to a team setting; it is our boundary choice, not an explicit rule from the article ([article: Versioning](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#versioning), [global styles](https://github.com/MaximeHeckel/design-system/blob/main/src/lib/globalStyles.ts)).
- **Document intent and change it deliberately.** Semantic token descriptions should state the role and relevant states/themes, not merely repeat a visual value. Changes to primitive values are implementation changes when roles remain stable; renaming/removing semantic roles or materially changing the design language should be treated as contract changes. This adapts Heckel's resilience and versioning rationale rather than quoting a naming standard he did not provide ([article: Color system](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#color-system), [article: Versioning](https://blog.maximeheckel.com/posts/building-a-design-system-from-scratch/#versioning)).
